# Decision and review record: coverage tool, report and pinning

## The change

Class I. Issue #74 (plan id M2a-82), part (a): the tool decision, its
pinning record, `cargo xtask coverage` and its `--self-test`, and
`tests/coverage/exclusions.txt`. The nightly job that runs the report is
wired by the nightly workflow's issue (#75), and part (b), the ratchet,
starts after a month of nightly figures (see "Ratchet start" below).

- `cargo xtask coverage` reads only the tool's JSON export (LLVM's
  `llvm-cov export` format with the tool's version added). It prints a
  Markdown report with four tables (testing specification 5.4, point 3):
  line, region and function coverage of library code per crate, each
  figure naming its target; branch coverage "not available"; doc-tests
  "not measured"; a crate not built on the target "not measured". Table 1
  also lists its uncovered functions once each: a generic function's
  instantiations are grouped by file and start position, as LLVM groups
  them, and count as run if any instantiation ran.
- The command fails, whatever the figures, when the export is empty,
  malformed or summary-only, was written by another tool version, counts a
  test file or an excluded file, or lacks an expected crate; when a crate
  is in no table or in two; and when an exclusion has no reason. Before it
  runs the tool it checks the installed tool's `--version`, and it refuses
  to start unless `IRONAFS_COVERAGE_JOB=1`, which only the nightly coverage
  job sets.
- `cargo xtask coverage --self-test` builds exports as JSON text, plants
  each failure case above, and runs them through the same reader, checks
  and report as the real run; a clean export must pass with "not
  available" in every branch cell. It never runs the tool. `cargo xtask
  check` and CI's lint job run it.

## The decision

Owner's decision (issue #74, "Decided by the owner"; testing specification,
the owner's decision 4): the coverage tool is cargo-llvm-cov 0.9.1, pinned,
a standalone tool under coding standards rule 21, installed as a prebuilt
binary whose checksum is verified before it runs, only in the nightly
coverage job, and run only behind `cargo xtask coverage`. That job holds no
secret and has a read-only token. The floors: report only for the first
month, then a ratchet on table 1's uncovered-line count; no absolute floor
and no percentage gate. The alternatives (our own `xtask` over rustc's flag
and the LLVM tools, absolute floors per crate kind, report only for good)
are not built.

A comparison made before implementing found nothing that contradicts the
decision's premises. INSPECTED, 2026-11-21:

- The rustc book, "Instrumentation-based code coverage": coverage needs the
  profiler runtime and the LLVM tools, through the `llvm-tools-preview`
  rustup component, whose tools and interface are "not currently subject to
  Rust's usual stability guarantees". Doc-test coverage needs unstable
  options. Both the tool and an own driver would depend on the same
  component.
- The pinned toolchain, 1.100.0 (LLVM 23.1.5): its distribution manifest
  (dated 2026-11-12) lists `llvm-tools-preview` as available for the
  `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu` hosts, and
  its standard library for both Linux targets carries the profiler runtime
  (`libprofiler_builtins`).
- An own driver needs no new tool, but it would have to find every test
  binary, keep stale build output out and merge one raw profile per test
  process. A missed binary would quietly lower the figures. The tool does
  that work, and because `xtask` reads only LLVM's export format, replacing
  the tool later changes one function (`run_tool`).

## Departures

- **Uncovered functions are keyed by file and start position, not by name.**
  The tool's JSON export keeps LLVM's mangled names. Its JSON path does not
  demangle them, and a generic function's instantiations have different
  mangled names. Demangling would need a third-party crate or a demangler
  of our own. LLVM itself groups instantiations by the start of the
  function's first region in its own file
  (`FunctionInstantiationSetCollector` in LLVM's
  `CoverageMapping.cpp`), and `xtask` uses the same key. The report lists
  `file:line:column`.
- **The real run refuses outside the job** (`IRONAFS_COVERAGE_JOB=1`). The
  issue states where the tool runs, but not how that is enforced. The
  variable makes it a property of the command, not only of the workflow.
