# Decision and review record: mutation testing and planted defects

## The change

Class I. Issue #73 (plan id M2a-79): the tool decision and its pinning
record, `cargo xtask mutants` (nightly shards and the pull-request run
over the diff) and `cargo xtask plant` with their `--self-test`, the
tool's configuration, `tests/mutants-accepted.txt`,
`tests/planted-defects.txt`, a nextest profile for mutation runs, and the
nightly jobs and the advisory pull-request job. Built on the nightly workflow's branch (#75), with `main`
merged in for `ironafs-time`, the only class S code landed so far.

- `cargo xtask mutants --shard k/4` runs one shard of cargo-mutants over
  the pure crates and `ironafs-client` (testing specification 5.4, point
  4). It refuses to start unless `IRONAFS_MUTANTS_JOB=1`, which only the
  nightly mutation jobs set, and unless the installed tool reports
  `cargo-mutants 27.1.0`. It lists the shard's mutants (`--list --json`),
  runs the shard with the same selection, `--no-shuffle`, nextest, the
  `mutants` profile, `--retries=0` and `--no-tests=fail`, writes the
  tool's console output to a file under the target directory, and reads
  only `outcomes.json`. It prints a Markdown report: counts per package
  (caught, missed, timed out, unviable, no result), each missed or
  timed-out mutant with its accepted reason or "new", and each mutant with
  no result. Only names of code leave the runner (5.5, point 2).
- `cargo xtask mutants --in-diff <file>` runs the mutants a pull
  request's diff touches in the pure crates, with the same tool checks,
  test arguments, classes and report. It refuses to start unless
  `IRONAFS_MUTANTS_PR_JOB=1`, which only the `mutants-diff` job of
  `ci.yml` sets (a separate variable: neither job's variable opens the
  other's run). It is report only: the reasons a result cannot be trusted
  are listed in the report under "Not trusted" and the command does not
  fail on them; a diff that touches no mutant says so. The job runs on
  pull requests only, with a read-only token, no secret, no artefact and
  no cache; it is not a dependency of `ci-ok`, and its run step continues
  on error, so it can neither fail nor satisfy a pull request (5.5, point
  1). Its diff is the merge commit against its first parent, the base.
  Pull-request reports are public; they hold only names of code and
  counts. The rule against publishing seeds, inputs or replay commands
  (the owner's decision 11) covers scheduled jobs, and the report holds
  none of them either.
- IronAFS's classes, not the tool's: a mutant is caught only when its test
  phase ran through nextest with `--retries 0` and exited 100 (tests
  failed). The tool also counts nextest's exit 4 (no tests run) and 101
  (build failed) as caught; here they are "no result". Unviable needs a
  failed build phase. A listed mutant with no outcome, or more than one,
  and an outcome that was not listed, are "no result".
- A shard fails when its result cannot be trusted: malformed output,
  another tool version, a missing or failed baseline, any mutant with no
  result, an accepted entry without a reason, a skip attribute in a
  mutated crate's source, or a nightly manifest without exactly one job
  per shard, or a whole unsharded run that lists no mutant (an exclusion
  that leaves nothing; a single shard may be empty). Survivors and timeouts are reported and do not fail it while
  mutation testing is report only.
- `cargo xtask plant` reads `tests/planted-defects.txt` and, for each
  guard, runs its test unplanted (it must pass), replaces the anchor (which
  must occur exactly the stated number of times), checks the file changed
  on disk, runs the test (it must fail with nextest's exit 100), restores
  the file and checks the restore. Anything else is "no result". The
  original is written back whatever happened, a failed plant write
  included; a restore that fails or cannot be verified stops the probe
  with an error saying the file may still hold the plant. Test output goes
  to a file under the target directory.
- The `--self-test` of each plants every failure case through the same
  code as the real run (planted tool output as text; an in-memory tree and
  a scripted test runner for the probe). `cargo xtask check` and CI's lint
  job run both.
- `.config/nextest.toml` gains the `mutants` profile: retries 0, fail
  fast, slow tests reported but never terminated. nextest reports a
  terminated test as failed, so the other profiles would count a mutant
  that only hangs as caught; cargo-mutants' own timeout classes it apart.
- `nightly.yml` gains `mutants-0` to `mutants-3` and `planted-defects`,
  each in `tests/tiers/nightly.txt`, so the freshness check fails a night
  that missed a shard.

## The decision

Owner's decision (issue #73, "Decided by the owner"; testing
specification, the owner's decision 3): the mutation tool is cargo-mutants,
pinned through the `add-dependency` checklist's tool-pinning items, a
standalone tool under coding standards rule 21; nightly over the pure
crates and `ironafs-client`, report only on pull requests, hand-planted
defects kept for every class S guard. The other options (IronAFS's own
mutator in `xtask`, planted defects by hand only) are not built. The exact
version is the implementer's choice under that decision, recorded below.

A comparison made before implementing found nothing that contradicts the
decision. An own mutator would need a Rust syntax walker of our own (rule
21 rules out a parser crate), plus the copy, build, timeout, shard and diff
machinery, several thousand lines; the reader, classes and report built
here are needed either way. INSPECTED, 2026-11-21: the tool's user guide
and source at tag v27.1.0 (`exit-codes.md`, `mutants-out.md`, `nextest.md`,
`shards.md`, `timeouts.md`, `stability.md`, `workspaces.md`, `in-diff.md`;
`src/cargo.rs`, `src/outcome.rs`, `src/process.rs`, `src/mutant.rs`,
`src/list.rs`), and nextest's exit codes at cargo-nextest 0.9.151
(`nextest-metadata/src/exit_codes.rs`). What they settle:

- Results are caught, missed, timeout and unviable; unviable means a check
  or build phase failed. `outcomes.json` records each phase's exit status
  and command line, and the tool's version.
- The tool counts nextest's "no tests run" (4) and "build failed" (101) in
  the test phase as caught (`NEXTEST_ALLOWED_CODES` in `cargo.rs`): the
  reason `xtask` classes from the recorded exit status.
- The output's format "is subject to change in future versions", and
  results may change between versions: the version is exact and the
  reader checks it.
- Shards have no coordination and must share their arguments; `--list`
  with `--shard` lists one shard: the run and the list share one
  selection, and each listed mutant must have one outcome.
- Results are deterministic when the tests are, with `--no-shuffle`.
- Each mutant runs only its own package's tests by default. A mutant
  caught only by another crate's tests is reported missed: an
  undercount, never an overcount.

## Departures

- **The run guards** (`IRONAFS_MUTANTS_JOB=1`, `IRONAFS_MUTANTS_PR_JOB=1`)
  are not in the issue; they make "only in these jobs" a property of the
  command, as #74 does for coverage.
- **The diff run reports instead of failing** on an untrusted result, and
  its step continues on error, so the advisory check is never red; the
  reasons are in the report.
- **A nextest profile for mutation runs**, not named in the issue or the
  specification: needed so a hang is a timeout, not a caught mutant.
- **The probe's tests run with the `mutants` profile** too, so a plant
  that only hangs ends at the job's timeout rather than as "caught".
- **Accepted entries are keyed without line and column** (`file: change`),
  so an entry survives edits above it. Two identical changes in one file
  share an entry.
- **A comment naming the skip attribute** in a mutated crate fails the run
  too: the check reads lines, not tokens, and the mutated crates have no
  reason to name it.
- **The branch merges `main`** into the nightly workflow's branch, so the
  plants have the class S code they name.

### Round 1: GLM, `310e4a2..643eed4`

not check offline (each recorded above as INSPECTED or EXECUTED), the run

dispositions:

1. **A failed write of the plant or of the restore did not attempt to
   restore the original**, and an interrupted run can leave a file
   planted. Fixed: the probe now writes the original back whatever
   happened after the plant was attempted, and reports a failed or
   unverified restore as an error saying the file may still hold the
   plant. Tests `probe_failed_plant_write_still_restores_the_original` and
   `probe_failed_restore_write_says_the_file_may_be_planted` (seen failing
   first), and a `plant --self-test` case. Not fixed: a run killed by a
   signal between the plant and the restore leaves the file planted, which
   `git status` shows; the nightly checkout is discarded, so this touches
   only development machines.
2. **Nothing required the four shards together to test anything.** Fixed:
   each shard also lists the whole unsharded run and fails if it lists no
   mutant. Test `a_whole_run_with_no_mutants_is_refused` (seen failing
   first) and a `mutants --self-test` case.
3. **nextest's exit codes were declared twice, and the logged subprocess
   run was duplicated.** Fixed: one module, `crates/xtask/src/nextest.rs`,
   holds the codes and `run_logged`, used by both commands. Tests
   `exit_codes_are_nextests` and
   `run_logged_appends_output_to_the_log_and_prints_none` (seen failing
   first).
