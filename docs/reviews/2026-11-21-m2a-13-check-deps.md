# Review record: `xtask` dependency, pure-crate and grant checks

## The change

Class I. Issue #46 (plan id M2a-13).

- `cargo xtask check-deps` reads the resolved graph from `cargo metadata`
  and enforces ADR 0004 C4's crate rules: every workspace crate is
  classified; pure crates depend only on pure crates; layers, drivers and
  `ironafs-client` have allow-lists; third-party crates are default-deny
  for every shipped crate; cryptography and foreign-function crates enter
  only through their home crates; nothing shipped depends on the test-only
  crates or on `xtask`. It also scans `ironafs-client`'s source for direct
  clocks, randomness, files, sockets, printing, `unsafe` and the macros
  that read files, and requires every member to inherit the workspace
  edition and lints.
- `cargo xtask check-pure` builds each pure crate with `cargo check --lib`
  for the six targets of `rust-toolchain.toml`, in dev and release,
  against a sysroot that holds only `core` and `alloc`, with
  `-F unsafe_code` set by the command. Around the build: the library root
  starts with an unconditional `#![no_std]`; no source file names `std`,
  `unsafe`, assembly, the macros that read files, `#[path]` or a
  fragment-built attribute or macro call; `extern` appears only as
  `extern crate alloc;`; tracked cargo configuration sets no compiler
  flags, wrapper or environment; and the dependency closure holds pure
  crates with no build script, procedural macro, native library or
  feature.
- `cargo xtask check-grants` keeps the AFS-3 rights evaluator's names
  inside their module and the codecs (ADR 0004 N28, point 2), and requires
  their definitions to be `pub(crate)` or narrower.
- The token reader these scans share fails closed where it could part
  from the compiler: literal suffixes, shebang lines and frontmatter
  fences are refused, and lifetimes are read whole.
- Each check has `--self-test`, which builds fixture workspaces, plants
  each violation and requires exactly the planted violations. CI's lint
  job and `cargo xtask check` run all three checks and their self-tests.
- **Design change during review.** After GLM round 3, the owner decided
  (2026-11-20) that every pure crate is unconditionally `#![no_std]` with
  `extern crate alloc`, so the compiler, not a source scan, keeps the pure
  crates off the operating system. A read-only GPT research seat
  (`gpt-6.2-sol`, high) and a Claude Mythos design check informed the
  decision; neither wrote any of this change. `cc6ce36` made the change:
  the std-path token rules for pure crates were deleted from `check-deps`
  and `check-pure` was added.
- Deliberate strictness, kept after the same-family check agreed:
  `include_str!` is refused even in a doc attribute, and the
  `$(#[$m:meta])*` macro pattern is refused, in pure crates and in
  `ironafs-client`.
- Not in this change, and not reviewed here: parts of #46's acceptance
  that the code does not hold (listed in the pull request).
- **Written by** `claude-code:claude-opus-5-5` (Claude Code subagents).

## Findings

GLM, round 1, all fixed in `251cfd7`:

- **Major:** the pure-crate scan skipped `tests.rs` and `tests/` by name,
  so an ungated `mod tests;` shipped unscanned code. A test module is now
  skipped only where its parent declares it under `#[cfg(test)]`.
- **Minor:** edges through a path package that is not a workspace member
  were invisible. The check walks every package of the resolved graph and
  fails on a local crate that is not a member under `crates/`.
- **Minor:** a pure crate's build script and binaries were never read. A
  build script or binary in a scanned crate now fails.
- **Minor:** `ironafs-client` could depend on a driver or a layer. It now
  depends on no driver, layer or binary, and its source is scanned.

GLM, round 2, all fixed in `09d0f4a`:

- **Major:** a guarded name could be laundered through an associated type
  in an allowed file. Every alias of a guarded name is flagged, and the
  guarded definitions must be `pub(crate)` or narrower.
- **Major:** `ironafs-client` could depend on any third-party crate not on
  the cryptography deny-list (a socket crate, for one). Every shipped crate
  now has a default-deny third-party list.
- **Minor:** `.collect()` into a `HashMap` used the random default hasher
  unseen. Pure crates may not name the std hash collections (extended to
  `ironafs-client` in `cc6ce36`).
- **Minor:** file-system method names matched the crates' own methods. The
  rule was limited to pure crates, and was removed with the other
  pure-crate token rules in `cc6ce36`.
- **Minor:** `impl Trait` in return position was taken for an impl block,
  hiding an alias in that function. The alias rule no longer depends on
  impl blocks.

GLM, round 3, all fixed in `cc6ce36`:

- **Major:** a renamed assembly macro (`use core::arch::asm as go;`)
  passed. Renamed assembly macros are refused; pure crates are also built
  with `-F unsafe_code`, which assembly needs.
- **Major:** requiring every member to inherit the workspace lints made
  the `unsafe` crates ADR 0004 plans (`ironafs-os`, under its own ADR)
  impossible to write. The check takes an ADR-named list of crates that
  keep their own lints (empty today), and `check-pure` sets the `unsafe`
  ban itself, so purity does not rest on a manifest.
- **Minor, fixed:** the manifest reader could be fooled by a TOML
  multi-line string (now refused); an import of a crate's own `print`
  was refused (imports from `crate`, `self` and `super` are allowed); a
  crate-private `extern "C"` definition was reported as public (now
  tested as private); `r#unsafe` as a name was refused (it is a name).

GLM, round 4:

- **Major, refuted:** that build scripts and procedural macros of the
  self-test's planted cases would be compiled against the trimmed
  sysroot, failing `check-pure --self-test` unconditionally. Evidence:
  `check-pure` always passes `--target`, and cargo then applies
  `CARGO_ENCODED_RUSTFLAGS` to target units only, not to host build
  scripts or procedural macros; on `7c6f97d` the self-test passed all 20
  planted cases, the build-script and procedural-macro cases among them,
  each failing for its planted reason (EXECUTED by the implementer). GLM
  accepted the refutation in round 5.
- **Minor, fixed (`858f830`):** `include!` or `#[path]` could bring in a
  file outside the library's directory. Both are refused, and every file
  of the package is read.
- **Minor, fixed (`858f830`):** a symbolic-link loop could make the walk
  recurse without bound. Symbolic links in a pure package are refused and
  not followed.

GLM, round 6:

- **Major, fixed (`6ad377a`):** the `ironafs-client` scan never refused
  `include_str!` or `include_bytes!`. All three file-reading macro names
  are refused there, and, independently of the token reader, as words in
  the raw text of every pure-package and client file.
- **Minor, resolved differently (`bafa1c3`):** a shebang line was refused
  as a stray `#`. It is now refused deliberately: the compiler skips it
  unread, which the reader cannot copy safely, and pure crates ship no
  binaries. GLM passed round 7 with this.

Claude self-check (summary; each was reproduced on the old code before
its fix, and confirmed resolved in the next round):

- Round 1: the checks did not run in CI (`e40213d`); edges through
  non-members, `tests` skipped by name, raw identifiers, macros building
  `std` paths, `#[path]` and `include!`, a narrow forbidden list,
  `check-grants` skipping `target` and hidden directories, a rename of a
  guarded name, and a dependency on `xtask` (`251cfd7`).
- Round 2: `unsafe extern` with an empty `[lints]` table,
  `ironafs-client` on a third-party crate, renamed built-in macros, hash
  maps seeded without a constructor name, and drivers without rules
  (`09d0f4a`).
- Round 3: `ironafs-client` reading the file system through
  `std::path`, the TOML multi-line string, and hash maps in
  `ironafs-client`, by a controller decision (`cc6ce36`).
- Round 4: a `#![no_std]` found in a comment while a `cfg_attr` kept
  `std` for `panic = "abort"` builds, and `include!` of a file outside the
  library (`858f830`).
- Round 5: `include!` and `#[path]` with the `!` or the brackets passed
  as a macro fragment (`9c0e811`, `ca56539`).
- Round 6: the token reader parted from the compiler on a literal suffix
  (`""r"\" "`), a lifetime spelled like a raw-string prefix, and `cr"..."`
  in edition 2018 (`bafa1c3`, `6ad377a`, `7ac6534`).
- Round 7, latent item, fixed (`af88a4b`): a frontmatter fence, which the
  compiler skips unread, would part the reader from the compiler once a
  toolchain stabilises frontmatter. A file whose first token is `---` is
  refused; GLM verified it in round 8.

The redesign came after the third round of fixes. Rounds 4 to 8 were fix
rounds on the new design, each closing evasions the previous round
found. GLM's last two rounds (7 and 8) found nothing, and the
self-check's last round found no blocker or major. The review stopped
there.
